# Filigrane: Void Linux + niri

Ce dépôt décrit la machine (paquets, services, dotfiles) et la distribution Filigrane. L'agent IA choisi (Claude Code, Codex, opencode: `FILI_AI`) se lance avec `fili-ai` (Mod+Y) et lit ce fichier quand il travaille ici (`CLAUDE.md` l'importe). Les conversations portent sur cette machine: config, paquets, services, niri, dépannage. Les dotfiles de `~` et `~/.config` sont des liens vers `dotfiles/` (`bootstrap.sh`).

La skill `filigrane` (`agents/skills/filigrane/`, liée dans `~/.claude/skills` et `~/.agents/skills`) contient le détail (usage, mises à jour, système, niri, ressources, identité visuelle). Ce fichier ne garde que les règles toujours actives. Tout travail visuel suit `agents/skills/filigrane/references/brand.md` (fichiers maîtres dans `brand/`), et toute interface (fili-shell, outils `fili-*`, thèmes) le skill `filigrane-ui` (`agents/skills/filigrane-ui/`, HIG inspirée du Mac OS X classique).

Mod+Y note l'application active (`fili-context`, fichier `~/.local/state/filigrane/context.json`, `$FILI_CONTEXT_FILE`; Claude Code le reçoit dans son prompt système). Si l'utilisateur dit « ceci », « ces fichiers », « ici », lire ce fichier (champs `selection`, `location`, `about`) avant de demander. Les chemins se traitent avec les outils shell; corbeille avec `gio trash`.

Modifier des fichiers pour l'utilisateur (renommer, déplacer, supprimer, copier, créer, en lot): `fili-tx` (`mv`, `mv -` pour un lot sur l'entrée standard, `trash`, `mkdir`, `cp`, `made`), jamais `mv`/`rm`/`cp` seuls. Une demande = une transaction: `fili-tx undo` la défait en une commande (`redo`, `status`). Après un changement, dire « `fili-tx undo` pour annuler »; pour annuler, lancer `fili-tx undo`, pas de reconstruction à la main (détail: skill `filigrane`, `references/files.md`).

Les applications, le shell et l'assistant se parlent par des **contrats de fichiers et de commandes, sans IA ni démon** (`docs/api.md`): contexte (`fili-context`), catalogue des commandes `ctl` (`shell/ctl/<app_id>.json`, format défini par `fili-api-lint`, que chaque application copie à l’identique; `fili-api list|show|check`), incidents (`fili-incident`, gestionnaires `shell/incident/<nom>.toml`: l'assistant s'y enregistre, il n'est pas requis), événements (`fili-event`). Filigrane doit fonctionner sans `fili-ai`; l'assistant est un client de ces contrats parmi d'autres. Une application qui ajoute une action ou un verbe `ctl` relance `python3 -I scripts/fili-api-lint --app . --write` (son `make check` échoue sinon).

## Règles dures

- Gestionnaire de paquets: **xbps** (jamais apt, pacman, dnf, brew, nix, flatpak). Init: **runit** (jamais systemctl ni journalctl). Root via `sudo`.
- Lecture seule d'abord pour diagnostiquer, cause en une ou deux phrases, puis correction.
- Avant de recharger la config niri: `niri validate`.
- Après un changement du fili-shell (`dotfiles/config/quickshell/`, scripts `bar-*`, `fili-*`): `tests/fili-shell/run.sh` doit passer avant le commit. Pendant le développement, `tests/fili-shell/run.sh --changed` ne lance que les vérifications touchées par `git status` (un correctif = un test écrit, branché dans `run.sh` avec `want`). Jamais de `git stash` ici (d'autres sessions éditent le dépôt en parallèle).
- fili-file (Casier) vit dans son propre dépôt `filigrane-os/fili-file` (clone de travail: `~/Projects/fili-file`), épinglé ici par `apps/fili-file/upstream` (url + tag). Pour le modifier: travailler là-bas (`make check` doit passer; la version se publie par un commit qui monte `version` dans `Cargo.toml` et ajoute sa section de `CHANGELOG.md`: le CI de `main` (`.github/workflows/ci.yml`, build + tests dans un conteneur Void) crée alors tout seul le tag `vX.Y.Z` (`facteur-vX.Y.Z` pour Facteur) et la release GitHub s'il passe; ne jamais tagger à la main), puis changer `ref` ici (`.github/workflows/bump-app-pins.yml` ouvre toute seule une PR « Pin <app> to <tag> » sur `develop` dès qu'un nouveau tag existe; `scripts/bump-app-pins.sh [--apply]` fait la même chose à la main) et lancer `tests/fili-shell/run.sh` (parité de thème avec le shell et anatomie de fenêtre de la version épinglée; sa suite complète ne tourne ici que si l'épingle change ou avec `FILI_APP_TESTS=1`, sinon c'est le CI de l'application; `FILI_SRC_FILI_FILE=~/Projects/fili-file` pour tester un clone local sans tag). `./bootstrap.sh --apps` déploie la version épinglée. **Avant de fusionner sur `main` le commit qui monte la version (c'est lui qui tague), déployer en local et faire tester l'utilisateur en live** (une seule version après son accord, pas une version par retouche). Les autres applications `fili-*` (fili-term, fili-mail, fili-im, fili-music, fili-recorder) ont le même CI et la même règle. Le fichier de repli du menu (`shell/appmenu/fili-file.json`), le brief de Lia (`shell/lia/fili-file.md`), le lanceur et l'icône vivent dans son dépôt et s'installent avec son paquet (`make install-data`); `scripts/check-shell-menu.py` de Casier (lancé par `make check`) garde le menu de la barre identique à celui de l'application.
- **Lia (fili-ai), l'assistant, vit dans son propre dépôt** `filigrane-os/fili-ai` (clone de travail: `~/Projects/fili-ai`), épinglé ici par `apps/fili-ai/upstream` (même règle que fili-file: `make check` là-bas, version publiée par le CI de `main`, jamais de tag à la main, test en live avant la version; tant qu'aucun tag n'existe la broche est `develop` et `FILI_SRC_FILI_AI=~/Projects/fili-ai` construit la copie de travail). Il apporte le démon (`fili-ai-daemon`), les sessions des agents (`fili-ai-session`), la fenêtre (`fili-ai-window`: tiroir Qt Quick sur le layer-shell via `layer-shell-qt`, une seule instance pilotée par `fili-ai toggle|show|here|act NOM`), le lanceur `fili-ai`, le module de barre `agent`, son menu de repli, son catalogue `ctl`, son gestionnaire d'incident (`shell/incident/lia.toml`) et les briefs (`data/prompts/`, `shell/lia/<app_id>.md`; `rob/` reste lu en repli). Filigrane marche sans lui. La distribution garde `AiState.qml` (lit `ui.json`), les réglages de l'agent (`ai.env`) et les skills.
- Toute application `fili-*` à fenêtre (fili-file, etc.) **expose son menu** au menu global de la fili-bar, avec toutes ses commandes et leurs raccourcis, jamais seulement des boutons ou un menu contextuel. Le menu vit dans la barre: **inutile de le dessiner dans la fenêtre**. Deux voies: une barre de menus du toolkit lue par AT-SPI (`GtkMenuBar`; vérifier avec `fili-appmenu menu PID`, JSON non `null`; la `MenuBar` de Qt Quick Controls n'exporte pas ses entrées, ne pas s'y fier), ou un menu de repli `dotfiles/config/filigrane/appmenu/<app_id>.json` (voir `bar/modules/appmenu/AppMenu.qml`, skill `filigrane-ui`, `references/hig.md` §7). Un repli ne lance que des commandes: pour qu'il couvre les vraies actions (copier, renommer, corbeille…), l'application les expose par une commande de contrôle (`fili-file ctl --pid PID action NOM`, `%pid` dans le fichier de repli), jamais par des frappes simulées; un fichier de repli passe devant AT-SPI. Le repli vit dans le dépôt de l'application (`shell/appmenu/<app_id>.json`, avec son brief de Lia `shell/lia/<app_id>.md`) et son `scripts/check-shell-menu.py` (lancé par `make test` ou `make check`) le garde en accord avec la fenêtre; le banc d'ici (`run.sh`) charge celui de l'application épinglée.

- La fili-bar est une liste de modules: un dossier `dotfiles/config/quickshell/bar/modules/<nom>/` avec son manifeste `module.toml` (`side`, `order`, `display`, `tray`, `show`), `<Nom>Module.qml` et son panneau `<Nom>Panel.qml` à côté; un manifeste avec `cmd` suffit pour un plugin script (sans QML). Les rangées par défaut viennent des manifestes; le `~/.config/filigrane/fili-bar.toml` facultatif les surcharge (listes `left`/`right`, `"..."` = les modules par défaut, `[modules.<nom>]`). Un module personnel (compte, service tiers) va dans `users/<login>/dotfiles/config/quickshell/bar/modules/<nom>/` ou est un plugin (`fili-bar new|install`, dans `~/.local/share/filigrane/bar/plugins/`), jamais dans la distribution. Le module d'une application `fili-*` vit dans le dépôt de l'application (`shell/fili-bar/<nom>/`, avec ses traductions `i18n/fr.json`) et s'installe avec son paquet; `fili-bar link-system` le relie à la barre (le dossier du dépôt ou un module personnel de même nom l'emporte). Détail: `docs/bar.md`, « Shipped by an application ». Détail: `docs/bar.md`, skill `filigrane-ui`, `references/hig.md` §5.
- **Demander à Lia depuis une application** (Mod+Ctrl+Y, entrée « Ask Lia… » du menu de la barre de toute application, déjà dans `appmenu/_default.json`): `fili-ai here` (sans texte) montre le **petit champ flottant** (`FiliAsk.qml`: Entrée envoie et ouvre le tiroir sur la nouvelle session; Maj+Entrée envoie sans l'ouvrir, la fin est alors annoncée par une notification); `fili-ai here TEXTE` ouvre directement le tiroir. Dans les deux cas la session de Lia est celle **cadrée** sur l'application active (une nouvelle session à chaque demande, liée à l'application; le tiroir reprend la plus récente); le démon ajoute à chaque message la consigne de rester dans ce périmètre (consigne du prompt, pas une barrière technique). Le prompt caché de la session (envoyé au premier message) vient de `agents/lia/_default.md`, du brief de l'application (commandes `ctl` de l'application, `fili-tx`, interdits: **toute application `fili-*` à menu de repli en a un**, `shell/lia/<app_id>.md` dans le dépôt de l'application, vérifié par son `scripts/check-shell-menu.py`; `agents/lia/<app_id>.md` ici ne sert qu'aux programmes sans dépôt propre) et `~/.config/filigrane/lia/<app_id>.md` (ajouts personnels). Le bouton d'en-tête `LiaButton.qml` (référence Casier) lance `fili-ai here`.
- **Kit d'interface `fili-ui`** (`filigrane-os/fili-ui`, clone `~/Projects/fili-ui`, module QML `Fili.UI`): boutons, champs, menus, dialogues, barre d'onglets (un onglet se déplace, se ferme et se détache toujours), en-tête, barre latérale, pied de page, info-bulle, panneau, réglages, icônes. Une application `fili-*` n'écrit pas ses propres copies: elle l'épingle par tag dans son `Cargo.toml` (Casier 1.18.0 est la référence; les autres suivent `docs/plan-fili-ui-rollout.md`), ici `libs/fili-ui/upstream`. Un composant manquant s'ajoute d'abord au kit (sa CI crée le tag `vX.Y.Z` depuis `Cargo.toml` + `CHANGELOG.md`, jamais de tag à la main), puis s'utilise. Aucun effet de shader (`MultiEffect`…): la session rend en logiciel. Comparaison avant/après d'une fenêtre: `scripts/fili-compare-ui`.
- Toute fenêtre d'application `fili-*` suit la même anatomie (`agents/skills/filigrane-ui/references/app-window.md`, référence Casier, pied de Facteur): en-tête 44 avec les boutons Fenêtre et Fermer à droite, barre latérale 200 aux en-têtes de section repliables, pied 28 sur fond `backgroundDeep` (Facteur), onglets de Facteur (bande 40, onglet 28), `KineticScroll` + `FiliScrollBar` sur toute vue défilante (jamais la barre de Qt), menu complet partagé avec la fili-bar. Contrôle: `tests/fili-shell/check-app-window.py --ref <casier> <app>`.
- En-tête et pied de page des applications `fili-*` (Réglages > Apparence, `fili-theme header|footer on|off`, `[window] header|footer` de `theme.toml` ou de `<app>.toml`, `--no-header` / `--no-footer` au lancement): chaque application les suit **en direct** (surveille `~/.config/filigrane/`), rien n'est accessible uniquement par l'en-tête (raccourci et menu de la barre), le pied réapparaît pour une opération, une erreur ou un avis (détail: `app-window.md`).
- Débogage des applications `fili-*`: chacune a un journal et un panneau Debug (menu Affichage > Debug Logs, Ctrl+Shift+L, journal sélectionnable au-dessus du pied de page), et un vrai bug (panique, erreur QML, « Ask Lia » du panneau) devient un incident (`fili-incident`, notification puis Lia; l'issue GitHub ou le +1 ne partent qu'avec l'accord de l'utilisateur, sans `gh` le formulaire s'ouvre dans le navigateur). Modèle Baladeur (`fili-music/src/logs.rs`, `DebugPanel.qml`), détail: `agents/skills/filigrane-ui/references/app-window.md`.
- Réglages d'une application `fili-*`: `dotfiles/config/filigrane/<app>.toml` (facultatif, créé seulement s'il y a un vrai réglage; l'état d'usage va dans `~/.local/state/filigrane/<app>/`, un dossier par application) et une entrée « Settings… » dans son menu de la barre qui l'ouvre avec `xdg-open` (détail: skill `filigrane-ui`, `references/hig.md`).
- Thème et options de toute application ou service Filigrane: dans son propre fichier `~/.config/filigrane/<app>.toml` (sections anglaises `[theme]`, `[theme.dark]`, `[theme.light]`, `[theme.accents]`), avec le global `~/.config/filigrane/theme.toml` en dessous et les défauts du dépôt tout en bas, comme fili-file (détail: skill `filigrane-ui`, `references/hig.md`).
- Nom affiché (alias): une application peut avoir un nom pour l'utilisateur différent de son programme (`fili-file` = « Casier »). L'alias est le nom partout dans l'OS (lanceur, menu de la barre, titres de raccourcis, « À propos de… »); le nom de programme ne reste que dans Filigrane (dépôt, commandes, code, app-id) et dans la fiche « À propos » (« Aussi connu sous le nom de »). Toute application à alias a cette fiche, ouverte par la commande `about` (menu de la barre, entrée « À propos de … »).

## Déclaratif

Tout changement durable va dans ce dépôt, pas seulement sur le système live, dans la bonne couche:
- **distribution** (générique, utile à tout utilisateur): paquets `packages/`, services `services/`, réglages par défaut `config.env`, configs `dotfiles/`, outils `apps/`.
- **matériel**: `hardware/<machine>/`.
- **personnel** (comptes, services tiers, goûts de l'utilisateur): `users/<login>/` (`config.env`, `packages/`, `dotfiles/`, `layer.sh`), couche active dans `.user-layer` (`none`: la créer, puis `./bootstrap.sh --user-layer <login>`). Même chemin qu'un fichier de la distribution = il le remplace. Niri: `users/<login>/dotfiles/config/niri/local.kdl`.
- Dans le doute, personnel. Rien de personnel (compte, URL de service, chemin `/home/<login>`) dans la couche distribution.
- Puis `./bootstrap.sh` (idempotent) et montrer `git diff`. Dépôt xbps et ISO: `distro/` (voir son README).

## Ressources

L'OS doit se faire oublier: le navigateur, les agents et les conteneurs passent avant. Choisir la solution la plus légère (paquet Void natif, pas de daemon inutile, pas d'Electron/JVM/Node résident, pas d'effets niri hors du flou derrière le menu). Si un paquet ou service est lourd, **avertir avant d'installer** (format dans la skill). Mesurer après toute installation durable (`budget save avant` puis `budget diff avant`). Pour un outil maison, préférer un binaire natif léger et rapide (Rust, dans `apps/`, compilé par `bootstrap.sh`) à un script qui charge un runtime lourd (Python/GTK, Node), quitte à compiler.

## Git

- Dépôt **public**: avant chaque commit, scanner le diff stagé (tokens, mots de passe, clés, e-mails, IP) et montrer le résultat.
- Commit autorisé sans demander après un changement terminé et vérifié (scan ci-dessus obligatoire, jamais d'attribution à un agent IA). Push autorisé sans demander sur toute branche autre que `main`; jamais de push sur `main` (ni force-push) sans demande explicite.

## Interdits

`install-void.sh` (efface un disque entier), `mkfs`, `wipefs`, `parted`, `dd` sur un disque, et toute modification de `/etc/sudoers*`, `~/.ssh`, des identifiants des agents (`~/.claude/.credentials.json`, `~/.codex/auth.json`, `~/.local/share/opencode/auth.json`).
Sans confirmation: installer un paquet (`xbps-install <pkg>`, avertissement ressources si lourd), `xbps-remove` simple d'un paquet non critique (avec Claude Code, le hook `guard-destructive.sh` redemande pour `base-system`, noyau, glibc, xbps, runit, sudo, niri, `-R`/`-f`), `rm` dans le scratchpad ou le dépôt, commit après un changement vérifié (voir Git).
Demander avant: mises à jour système (`xbps-install -u/-Su`), `sv restart/stop` (services système), `rm` ailleurs, édition de `/etc`, bootloader, reboot, push sur `main`. Avec Claude Code et Codex, `sv` et `xbps-*` passent sans mot de passe sudo: la confirmation vient de l'agent (permissions et hook de Claude Code, bac à sable de Codex). Avec opencode, sudo garde son mot de passe: donner la commande à lancer.
Choix de conception (valeur, réglage, outil): prendre le défaut raisonnable, le dire en une ligne, ne pas poser de question. Après un remplacement validé par l'usage, nettoyer l'ancien (paquet, config) sans redemander.

## Style

Réponses en français, courtes et factuelles. Dire ce qui a été fait, vérifié ou non testé.

**Code en anglais** (projet open source): tout ce qui est écrit dans le dépôt est en anglais: code, identifiants, commentaires, messages de commit, documentation, **commentaires des fichiers de configuration** (`dotfiles/`, `users/`, `.toml`, `.kdl`, `.conf`), messages de la ligne de commande et chaînes d'interface (les traductions vont dans les fichiers de langue). Seules les réponses à l'utilisateur dans la conversation restent en français. Un fichier touché qui contient encore du français est traduit au passage.
